# データストレージ移行検討

## 結論（先に）

**当面は現状の JSON + Git 管理を継続**。将来の限界が見えてきたら **Cloudflare D1** への移行を第一候補とする。

理由:
1. 現状 288KB / 43アーティストで JSON で十分動く（100倍に増えても 30MB 程度）
2. Cloudflare Pages Functions と D1 が同じ Cloudflare エコシステムで運用シンプル
3. 認証が必要になった時は Supabase 検討も視野

## 現状の規模（2026-04-12時点）

| 項目 | 値 |
|------|-----|
| アーティスト数 | 43 |
| 合計レコード数 | 216 |
| 合計アノテーション数 | 75 |
| `data/` 総サイズ | **288KB** |
| 最大ファイル | 8.4KB |

予測:
- アーティスト 100 → ~700KB
- アーティスト 1,000 → ~7MB
- アーティスト 10,000 → ~70MB
- 各アーティスト 1年分の日次レコード → 上記の 2-3倍

## 評価軸

1. **コスト**: 無料枠の範囲、有料化時の料金
2. **学習コスト**: 既存の開発フローからの移行のしやすさ
3. **スケーラビリティ**: アーティスト数が増えた時の挙動
4. **認証連携**: 将来のマルチユーザー対応のしやすさ
5. **開発体験**: ローカル開発・マイグレーション・バックアップ
6. **データ可搬性**: ベンダーロックインの度合い
7. **運用コスト**: 金銭・労力ともにできるだけ低く保ちたい（プロジェクト方針）

## 選択肢比較

### 1. 継続 JSON + Git（現状）

| 軸 | 評価 | コメント |
|---|---|---|
| コスト | ✅ 完全無料 | Git とファイルシステム |
| 学習コスト | ✅ ゼロ | 既存フロー |
| スケーラビリティ | △ 数MB〜数十MBが現実的限界 | フロントが全件読むため |
| 認証連携 | ❌ なし | 別途必要 |
| 開発体験 | ✅ シンプル | テキストで diff/edit/grep |
| データ可搬性 | ✅ 完全 | ただの JSON |
| 運用コスト | ✅ ゼロ | |

**長所**: 圧倒的にシンプル、データの完全な可搬性、無料、Git で履歴管理
**短所**: 全件 fetch のため大規模化に弱い、複雑なクエリができない、リアルタイム書き込み不可

**限界の目安**:
- 1リクエストの転送量 > 5MB（モバイル考慮）
- アーティスト数 > 200
- ユーザー認証が必要になった時

### 2. Cloudflare D1（推奨候補）

SQLite 互換のサーバーレス DB、Cloudflare Pages Functions と同一エコシステム。

| 軸 | 評価 | コメント |
|---|---|---|
| コスト | ✅ 無料枠あり | 5GB ストレージ / 5億行 reads / 1億行 writes per month |
| 学習コスト | ⚪ 中 | SQL（SQLite方言）、wrangler の知識 |
| スケーラビリティ | ✅ 数十GBまで | エッジ展開で高速 |
| 認証連携 | △ なし | Cloudflare Access or 自前実装 |
| 開発体験 | ⚪ wrangler dev でローカル | マイグレーション仕組みあり |
| データ可搬性 | ⚪ SQLite | dump で SQL 出力可能 |
| 運用コスト | ✅ 低 | サーバーレス・課金は使った分のみ |

**長所**:
- Cloudflare Pages Functions から直接 binding 経由でアクセス
- SQLite 互換なのでローカル開発が簡単
- 既存の Cloudflare デプロイに統合
- 無料枠が広い

**短所**:
- ベータ機能（GA だが新しめ）
- 認証は別途実装必要
- フロント直接アクセス不可（Functions経由）

### 3. Supabase

PostgreSQL + 認証 + Storage + Realtime + Edge Functions の総合 BaaS。

| 軸 | 評価 | コメント |
|---|---|---|
| コスト | ⚪ 無料枠あり | 500MB DB / 1GB Storage / 50k MAU |
| 学習コスト | ⚪ 中 | PostgreSQL + Supabase 独自概念 |
| スケーラビリティ | ✅ 大規模対応 | PostgreSQL なので強い |
| 認証連携 | ✅ 標準装備 | Email/OAuth/Magic Link 等 |
| 開発体験 | ✅ ダッシュボード優秀 | マイグレーション・型生成 |
| データ可搬性 | ⚪ PostgreSQL | dump で SQL 出力 |
| 運用コスト | ⚪ 中 | 無料枠超えで $25/月〜 |

**長所**:
- 認証 / Realtime / Storage が標準装備
- ダッシュボードが優秀
- フロントから直接 SDK でアクセス可能
- TypeScript 型自動生成
- マルチユーザー対応のしやすさ

**短所**:
- Cloudflare エコシステムから外れる（運用箇所が増える）
- 無料枠が D1 より狭い（500MB）
- 7日間アクセスなしで一時停止される
- 学習コスト中（標準 PostgreSQL に Supabase 独自レイヤー）

### 4. Turso

SQLite 互換、libSQL ベース、エッジ対応。

| 軸 | 評価 | コメント |
|---|---|---|
| コスト | ✅ 無料枠 9GB | 500 DB / 10億 reads per month |
| 学習コスト | ⚪ 中 | SQL + Turso CLI |
| スケーラビリティ | ✅ エッジ展開 | 複数リージョンへ自動レプリカ |
| 認証連携 | ❌ なし | 別途必要 |
| 開発体験 | ⚪ CLI 中心 | ローカル開発OK |
| データ可搬性 | ✅ SQLite | 標準 SQLite ファイル |
| 運用コスト | ✅ 低 | サーバーレス |

**長所**: D1 と似た構造で、Cloudflare に依存しない選択肢
**短所**: Cloudflare Pages Functions との統合は D1 より手間

## 移行判断基準

以下のいずれかが発生したら移行検討を始める：

1. **アーティスト数 > 200** — 全件 fetch のフロント設計に限界
2. **`data/` 合計サイズ > 10MB** — モバイル転送量のしきい値
3. **マルチユーザー対応が必要** — 認証・ユーザー別データが必要に
4. **複雑なクエリ要件** — 期間集計・集約・全文検索など、フロントで処理困難
5. **書き込み頻度の増加** — Add Artist フォーム以外の書き込みが増えた時
6. **データ漏洩リスクの懸念** — 公開リポジトリで管理しにくい情報を持つ場合

## 推奨移行パス

```
[現状 JSON + Git]
        ↓ アーティスト数 > 200 OR 認証不要
   [Cloudflare D1]  ← 第一候補
        ↓ マルチユーザー化
     [Supabase]    ← 認証必要時
```

### 第一段階: D1 移行（認証なし）
- collector → D1 へ書き込み（Cloudflare API 経由）
- frontend → Pages Functions 経由で読み取り
- 書き込み: collector のみ、フロントからは Add Artist 経由のみ
- 既存 JSON は import スクリプトで一括投入
- フロントの useArtistData hook を fetch から API call に置換

### 第二段階: Supabase 移行（認証必要時）
- D1 では認証が手間 → Supabase へ
- ユーザー登録・ログイン・プラン管理（無料/有料）
- アーティスト個人別のお気に入り・通知設定など

## 段階的なリスク軽減策（移行前にできること）

JSON のまま運用を続けつつ、限界を遅らせる方法：

1. **データの分割配信**: 現在の `useAggregatedArtistData` を `useArtistData` に切り替え、選択時のみ fetch
2. **インデックスファイル**: アーティスト一覧は config.json から、詳細は個別ファイルから取得（既存の構造）
3. **CDN キャッシュ最適化**: Cloudflare の Cache-Control ヘッダーで再取得を抑制
4. **過去データの圧縮**: 90日以上前のレコードを別ファイル `data/{id}-archive.json` に分離
